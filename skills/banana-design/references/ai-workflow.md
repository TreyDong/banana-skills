# Banana Design · 约束 AI 生成界面

这份文件的目的是：让 AI 写界面时少返工，且产出符合设计系统。

## 一、给 AI 派任务之前

先把这四样东西一起给过去，缺一项 AI 就会自己发明：

1. **token 文件的路径**（`assets/banana-tokens.css` 或项目里的设计 token）
2. **组件库的名称与用法边界**（用什么、明确不用什么）
3. **禁用写法清单**（本文件第六节）
4. **验收标准**（什么样的结果算做完）

然后按下面写任务：

- 一次只解决一个问题。看到别的问题只记一行遗留，不顺手改。
- 抽象指令先归一化：把"好看一点""高级感"翻译成"改哪里、看到什么算改好了"。翻译不了就问用户，不猜。
- 授权范围：只有任务本身包含规范维护时，才去改项目的规范文件或本 Skill。一次界面任务不顺手改规则文件。
- 审美要求写成可观察的验收条件：布局、字阶、色彩、状态各自要满足什么。具体效果沿用项目视觉语言，不指定毛玻璃或渐变这类做法——那会和很多项目自己的"禁止装饰性渐变与玻璃效果"打架。
- 给正误对照。每条禁用写法配一段错误示例和一段正确示例。
- 明确"不是什么"。点框架名时同时说明它不是哪个相似框架。

## 二、规则文件怎么组织

从各家实践看，稳定的三层结构：

```
项目根 AGENTS.md        只做导航与硬禁令，控制在 8KB 以内
  └─ 嵌套 AGENTS.md    某个目录的契约，5KB 以内。改这个目录前必读
  └─ skills/           按功能域拆的细则，写明触发条件与不触发条件
  └─ DESIGN.md         视觉系统与品牌的唯一依据
```

规则文件写法：

- 一条一个 bullet，祈使句，最多一个说明防住什么失败。
- 已有自动检查覆盖的规则，只写一行指向该检查的指针。
- 同一类错误复发或被评审抓到，规则才进文件；单次教训写进提交信息。
- 一个主题只保留一个唯一依据，其他文件只引用不复制定义。
- 规则文件只做路由：知道契约就读契约，不知道先查索引，不要一次加载全部文档。
- 组件专属文档只在"类型 / 示例 / 上游文档都表达不了"时才写，禁止为完备而写。

规则分层：`structure > lint > rule > style`。能用"出现了 X"或"做了 X 却没有 Y"描述的规则，写成 lint 脚本而不是文字规则。只能主观判断的规则必须写清为什么不能写成代码。同一现象第二次出现，必须把规则升层。

## 三、规则自维护

- 规则与产出不符时，主动修订规则并在回复里明说。
- 通用经验去掉项目名后仍成立，才回流上游。回流的是判据，不是具体取值。
- 回流顺序：失败用例 → 反例 → 加规则（默认 WARN）→ 登记 reference → bump 版本 → CHANGELOG → 测试全绿。
- 如果目标框架或组件库的 API 与模型记忆不同，规则里要写"先读本地文档 / 已安装的类型声明"，避免模型按旧记忆写。

## 四、给 AI 的祈使句写法

把设计规范翻译成 AI 能执行的行为，十种手法：

| 手法 | 例子 |
| --- | --- |
| 审美判断 → 文件指针 | "做界面前先读 `DESIGN.md` 的色彩一节" |
| "要好看" → 允许/禁止清单 | "允许毛玻璃与渐变底，禁止霓虹光效与玻璃拟态卡片" |
| 组件怎么做 → 复用判据 | "先在组件库索引里找，找不到再问" |
| 注意体验 → 状态矩阵 | "每个组件覆盖空 / 加载 / 错误 / 成功四态" |
| 检查 → 可执行命令 | "跑 `npm run check`，失败必须修" |
| 对齐设计 → 断言分级 | "截图比对：布局偏差 ≤ 2px，颜色取 token 名比对" |
| 说清楚 → 产物格式契约 | "每条评审结论带文件行号、触发场景、修复方向" |
| 人类专属 → 显式圈出 | "`HUMAN:` 段落由人写，AI 不得代笔" |
| 反训练数据偏置 | "这个项目用的不是 Next.js，是 TanStack Router" |
| 规则自维护 | "改完对照本文件，发现不符就更新本文件并说明" |

## 五、评审流程

四步：

1. **定范围**：这次改动碰了哪些界面、哪些组件。
2. **读代码与适用规则**：只读受影响的规则包，不整包加载。
3. **追消费者**：改一个共享组件，列出所有用到的地方。
4. **验证可观测后果**：这个改动在什么场景下会出什么问题。

结论分级：

- P0 阻断：功能不可用、数据错误、无障碍严重缺陷
- P1 高：主要路径出错
- P2 中：边界情况、体验明显不对
- P3 低：默认不报

每条结论带：文件行号、触发场景或所违反的规则、具体修复方向。

只报可观测缺陷或明确的契约违反。不把"更喜欢的写法"当缺陷，不写夸奖段，不写投机性风险。

## 六、明确禁止项

**颜色与样式**

- 禁止裸 hex、裸 rgba、裸调色板类名（`text-gray-400`）
- 禁止任意值类名（`p-[13px]`、`text-[#333]`）
- 禁止 `margin-*` 与 `space-x-*` / `space-y-*`
- 禁止在组件里另写 `font-family`
- 禁止内联样式对象表达能用类或变量表达的样式
- 禁止关闭任何 lint 规则（除用户明确批准）
- 禁止改依赖与工具配置（除用户明确要求）；改 lint / TS 规则必须先问人

**组件**

- 禁止 `div role="button"` / `div onClick`
- 禁止正数 tabIndex
- 禁止移除焦点轮廓
- 禁止 placeholder 当 label
- 禁止自造 modal 遮罩
- 禁止重新实现库里已有的组件
- 禁止写遮蔽既有契约的二次包装层
- 禁止自造生成式图标文件

**状态**

- 禁止只做 happy path
- 禁止用"关功能、删动画、放宽 API"的方式修 bug
- 禁止把降级体验当作修好
- 禁止给每一行进度指示器都加 `role="status"`
- 禁止数字加载失败时显示占位数值

**文案**

- 禁止说教式鼓励、宏大叙事、过度拟人化
- 禁止"不是 X 而是 Y"的铺垫句式
- 禁止 `simply` / `just` / `seamlessly` / `effortlessly`
- 禁止界面文案里用冒号（代码、命令、URL、时间、数据标签除外）

**协作**

- 禁止替人做人类专属动作：lint / TS 规则改动、依赖版本豁免、对外发布内容、`HUMAN:` 段落
- 禁止在依赖未安装时跑 formatter / `--fix`，避免全仓重排
- 禁止直接跑 `npx eslint` / `npx prettier` / `npx tsc`，只用仓库封装的命令
- 禁止在测试里污染生产代码：不加测试专用导出、参数、开关、全局量

## 七、可执行检查

> 以下命令**只产出候选项**，不是合规结论。命中项要人工判定：token 定义文件、登记过的例外、代码块里的示例都会误命中。零匹配也不代表合规，只代表没命中这些模式。


```bash
# 裸色与调色板类
rg -n "(text|bg|border)-(red|blue|green|gray|zinc|slate|neutral|stone)-[0-9]{2,3}" --glob '*.{tsx,ts,jsx,vue,svelte}'

# 裸 hex / rgba
rg -n "#[0-9a-fA-F]{3,8}\b|rgba?\(" --glob '*.{tsx,ts,css,vue,svelte}'

# 任意值类名
rg -n "\[[0-9]+px\]" --glob '*.{tsx,ts,vue,svelte}'

# margin 与 space-*
rg -n "\bm[trblxy]?-[0-9]|\bspace-[xy]-" --glob '*.{tsx,ts,vue,svelte}'

# div 冒充按钮
rg -n "<div[^>]*role=\"button\"|<div[^>]*onClick" --glob '*.{tsx,jsx,vue,svelte}'

# outline: none
rg -n "outline:\s*none|outline-none" --glob '*.{tsx,ts,css}'

# 内联样式
rg -n "style=\{\{" --glob '*.{tsx,jsx,vue,svelte}'

# 焦点轮廓被移除但没补 focus-visible
rg -n "focus:outline-none" --glob '*.{tsx,jsx,vue,svelte}'
```

人工确认项（脚本查不出来）：

- [ ] 四个状态都做齐，且每个都说了正在发生什么
- [ ] 键盘走一遍主流程，焦点顺序和可见性都对
- [ ] 窄屏 360px 与宽屏各看一次
- [ ] 明暗两套对比度都验过
- [ ] 减弱动效偏好下仍可理解
- [ ] 中文输入法组字时不会误触发
- [ ] 截图核对过，不只是代码审过

## 八、设计稿到代码

如果来源是 Figma 或设计稿：

- 先取设计稿的截图作为视觉比对目标，但截图不进代码。
- 代码只依据结构数据写。
- 改之前先看项目里已装的设计库依赖，复用现成组件、资源、token。
- 已连通到组件库的组件直接复用，"重新调样式"不算例外。
- 每个可见资源核四项：本地文件、设计槽位、调用点、渲染几何。一个不一致即失败。
- 只查本次范围，不动范围外的既有问题。
- 字体必须显式断言正确，脚本不报错不代表字体对。
- 查产品字体从源码查，不默认 Inter。
- 有设计系统变量就不许写死 hex 和像素间距。
- 设计稿导出的 `leading-none`、实心行高只用于图标，文本要用 token 行高。
- 13px 文本至少配 16px 行高，否则 g / j / p / q / y 会被裁。

## 九、人类专属清单

碰到这些，停下请人：

- 改 lint 规则、TypeScript 严格度、构建配置
- 改依赖版本、豁免版本策略
- 决定"这两个设计哪个是对的"这类审美裁决
- 对外发布、改品牌资产
- 写给外部看的内容（公告、说明、PR 正文里的 `HUMAN:` 段）
