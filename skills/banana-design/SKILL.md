# Banana Design

从 18 个高星开源项目（lobehub、open-webui、dify、langflow、cline、Roo-Code、continue、opencode、bolt.diy、dyad、vibe-kanban、jan、UI-TARS、assistant-ui、CopilotKit、tambo、OpenHands、Flowise）的源码与规范文件里蒸馏出的一套界面规则。

细则不在这里，按需读 `references/`。

## 0. 这份规范的性质

读之前先分清三类内容，别把默认值当成共识：

| 类别 | 含义 | 例子 |
| --- | --- | --- |
| **来源共识** | 多个项目独立采用同一做法 | 4px 间距刻度、语义 token 优先、审批动作靠近输入框、对比度 4.5:1 |
| **单项目做法** | 只有一个项目这么写，是可选风格不是硬规则 | lobehub 的 20 个语义色、opencode 的 147 个原始色、vibe-kanban 的看板布局 |
| **Banana 默认值** | 为了能直接落地，本规范自己选定 | 圆角基准 0.625rem、控件高 28/36/40、断点表、报告层 2px 细分网格 |

逐条来源见 `references/sources.md`。**引用某条规则时说明它是哪一类**；对方要的是"行业怎么做"就引共识类，要的是"我们怎么做"就用默认值。

## 1. 什么时候用

- 写、改任何界面代码之前
- 评审界面改动时（自检清单在第 7 节）
- 给 AI 派 UI 任务之前，先读 `references/ai-workflow.md`

## 2. 三条总原则

1. **语义优先于数值。** 颜色、间距、圆角、动效走 token，不写裸值。发现自己要写 `#fff`、`margin-top: 13px`、`text-gray-400`，就是该换 token 了。
2. **复用优先于重造。** 有现成组件就复用，有现成原语就套原语。只有库里完全没有对应物时才自己写底层。
3. **状态是设计的一部分。** 列出这个功能可能出现的加载、空、错误、成功状态，对实际可能发生的那些给出说明和可执行的下一步。

## 3. 动手流程

0. **先定制品与目标。** 产出来是什么——产品界面、幻灯片、长文报告、数据大屏、营销页、邮件，各自关注点不同；再定谁在什么场景看，写一句目标：「〈受众〉在〈场景〉下，〈时间〉内先看到〈主信息〉，然后〈动作〉」。制品与场景的策略表、幻灯片生产参数、按制品换的验收方式都在 `references/artifacts.md`。本文件其余章节默认在讲产品界面。
1. 先读项目内最近的设计规范文件（`DESIGN.md`、`AGENTS.md`、design token）。没有就按本规范默认值做，并在交付说明里写清用了哪些默认值。
2. 确认技术栈：用什么组件库、用 Tailwind 还是 CSS 变量、深浅色怎么切换。项目已有的一律沿用。
3. 查第 4 节速查表与 `references/tokens.md`，确认要用哪个语义 token。
4. 写代码，只用项目已装的原语和组件。
5. 过第 7 节自检清单；能跑的检查命令在 `references/ai-workflow.md` 末节。
6. 有视觉改动时截图核对，不能靠"代码看起来对"。

## 4. 速查表（Banana 默认值）

| 项 | 取值 |
| --- | --- |
| 间距刻度 | 4px 基准：4 / 8 / 12 / 16 / 20 / 24 / 32。报告排版层用 2px 细分 |
| 圆角 | 基准 0.625rem（根字号 16px 时是 10px），派生 4 / 6 / 8 / 10 / 14；页面 0；药丸 9999 |
| 正文字号 | 12 / 14 / 16，各字号对应行高见 `references/tokens.md` |
| 控件高度 | 28 / 36 / 40；触控目标 ≥ 44px |
| 容器宽度 | 阅读正文 768px；对话 880px；报告正文列 860px |
| 层级 | `--layer-panel 40 / floating 60 / modal 80 / modal-floating 90 / toast 100` |
| 动效 | 状态变化与浮层 100–200ms，浮层 ≤ 300ms |
| 对比度 | 正文 ≥ 4.5:1，控件与图标 ≥ 3:1，明暗两套都要过 |

边框 1px、阴影三档、焦点 2px 环、断点测试宽度等其余默认值见 `references/tokens.md`。

## 5. 硬规则摘要

细则在对应文件，这里只列最容易违反的几条。

**色彩与主题**（`references/tokens.md`）
- 颜色、圆角、阴影、字体、动效时长一律走语义 token，代码里不出现裸 hex、裸 rgba、裸调色板类名。
- token 名字编码角色，不编码外观；同名 token 在明暗两套主题下解析到不同值，只按名字消费。
- 状态色给背景、前景、边框三件套；没有对应 token 时先扩 schema，不许借用"最像的那个"。
- 一个界面只保留一个强色；品牌色只做标记，不做阅读背景。

**排版**
- 字号取自 token，正文只用 12 / 14 / 16，不存在 13px（13px 见 `references/tokens.md` 的代码字号）。
- 等宽字体只用于代码、命令、包名、路径、标识符、版本号。
- 每页只放一个 h1；正文阅读宽度约 70 个英文字符。

**间距与尺寸**
- 间距只用刻度值。组件内布局间距优先用 gap 与 padding；需要 margin 时说明用途并用间距 token。
- 嵌套表面要贴合时，内层圆角取 `max(0, 外层圆角 − 内边距)`；同级控件用同一圆角。
- 页面本身圆角为 0；浮层不做直角；通栏区域不做圆角。

**组件与样式**
- 优先用项目已有的组件库原语；项目用 CVA 与 `cn` 时沿用它们。
- 变体用 CVA，类名合并用 `cn`，颜色尺寸走 token。
- 状态样式优先用原语的 `data-*` 属性与 CSS 变量。
- 一个视图只放一个 primary 按钮。
- 图标走既有集合，禁止自造生成式图标文件；品牌图标用官方 SVG。

**交互与状态**
- 内容加载且布局可预知时用骨架屏或预留空间；短暂操作用带可访问名称的 spinner。
- 每个状态说明正在发生什么，并给出可执行的下一步；给不出下一步就别加这个状态。
- 工具执行细节留在消息流，批准与拒绝按钮固定在输入框附近；请求未完成时禁用按钮，响应后按请求身份加锁。
- 复制这类操作就地反馈并通过 live region 播报，不用 toast。

**可访问性**
- 正文对比度 ≥ 4.5:1，控件与图标 ≥ 3:1，明暗两套都过。
- 每个可交互元素有可见的 `:focus-visible` 焦点环。
- 装饰性 SVG 标 `aria-hidden="true"`，纯图标控件给可访问名。
- 布局用逻辑属性，支持 RTL。
- 禁止把交互元素写成 `div role="button"` / `div onClick`，禁止正数 tabIndex，禁止 placeholder 当 label，禁止自造 modal 遮罩。

**文案**
- 同一动作全站同一个动词；动作名用"动词 + 名词"。
- 进行中用现在分词加省略号。
- 界面文案里不用冒号（代码、命令、URL、时间、数据标签除外）；写陈述句，不用反问句。
- 空位就留空，不为配版面写一句话。

**输出形态**（`references/tokens.md` 末节）
- 内容超过一屏不要把 Markdown 直译成 HTML。改版式：封面、章节编号、目录、图示。
- 一页只放一个强色；数字集中到一处；层级靠对比和留白，不靠线。
- 幻灯片、大屏等其他制品的画布、字号与专项禁则见 `references/artifacts.md`。
- 交付前用真实浏览器截图看一眼，别凭代码想象效果。

**补充规则**（来自治理底稿，容易被忽略）
- 改某个目录的代码前，先读那个目录适用的嵌套规则文件。
- 改公开主题 token 后，验证明暗默认主题与自定义主题的回退路径都还能用。
- 有多个异步阶段的功能，用一个可辨识联合体表达阶段，不用多个布尔量或可空字段拼状态。
- 修界面问题定位根因，并验证修复没有降低键盘、响应式或既有功能体验。
- 内容异步进入页面时预留空间，避免可见的布局跳动。
- 按设计稿还原界面时，先取截图作视觉对照，再核对项目已有组件、资源和 token。
- 改了界面文案就按产品行为变化验收，不因为"只是改文案"跳过检查。

## 6. 让 AI 生成界面

给任务之前把四样东西一起给过去，缺一项 AI 就会自己发明：token 文件路径、组件库边界、禁用写法清单、验收标准。

完整的流程、祈使句写法、禁止项、检查命令与人工确认项在 `references/ai-workflow.md`。三条最容易漏的：

1. **抽象指令先归一化。** 把"好看一点"翻译成"改哪里、看到什么算改好了"；翻译不了就问，不猜。
2. **审美要求写成可观察的验收条件**，具体效果沿用项目视觉语言，不指定具体效果（毛玻璃、渐变）——那会和项目自己的禁装饰规则打架。
3. **一次只解决一个问题。** 看到别的问题只记一行遗留。

## 7. 自检清单

- [ ] 颜色、间距、圆角、字号全部来自 token，没有裸值和任意值
- [ ] 组件内间距用 gap 与 padding；用了 margin 的地方说明了用途
- [ ] 一个视图只有一个 primary 按钮
- [ ] 可能的加载、空、错误、成功状态都列了，实际可能发生的那些有说明和下一步
- [ ] 所有可交互元素有可见焦点环，键盘可达
- [ ] 正文对比度 ≥ 4.5:1，控件 ≥ 3:1，明暗两套都验过
- [ ] 动效时长在 100–300ms，不动会触发布局的属性，支持减弱动效
- [ ] 中文输入法组字期间不会误触发快捷键
- [ ] 窄屏（≤360px）不横向滚动，文字不溢出
- [ ] 工具调用的详情与批准按钮位置分得开
- [ ] 文案统一动词，动作名是"动词 + 名词"
- [ ] 有视觉改动，截图核对过

可执行检查命令见 `references/ai-workflow.md` 末节——注意那些命令只产出候选项，零匹配不等于合规。

## 8. 与项目冲突时

顺序：

1. 项目 `DESIGN.md` / `AGENTS.md` 明确写了 → 照项目来。
2. 项目只是"没写" → 用本规范默认值，并在交付说明里写明用了哪些默认值。
3. 本规范与项目现实冲突 → 用项目做法，并在回复里说明差异。

**只有任务授权包含规范维护时，才修改规范文件**（项目的或本文件的）。一次界面任务不顺手改规则文件。

规则能写成脚本的就写成脚本，不要靠文字约束。能用"出现了 X"或计数描述的规则，不要写成"应该注意 X"。
